# 多 Agent 编排 · 产品需求说明书（PRD）

> 这是提炼后的**产品决策文档**，面向决策与对齐。技术调研与参考项目证据见 [`../research/multi-agent-orchestration.md`](../research/multi-agent-orchestration.md)（证据底座，不作为决策阅读材料）。

## 1. 一句话定位

让你（一个人）像管一个团队一样管多个 AI agent——**讨论方向、派活、盯进度、随时插手细节**。

## 2. 为什么做

现在你只能一个个手动起 agent，它们互不认识，你得全程盯着每一步。我们要让你从「**操作员**」变成「**老板**」：agent 自己分工协作，你只管定方向和拍板。

这是项目的终极目标 **OPC（一人公司）**：一个人通过编排多个 AI agent，完成传统需要一个团队的工作量。

## 3. 给谁用

- **一人公司 / 超级个体**：一个人干一个团队的活（开发、调研、规划、review 同时推进）。
- **小团队**：几个人协调多个 agent 协作。

主要入口是浏览器（含手机），服务器跑真实 agent。

## 4. 三个核心概念（整个产品就这三样）

| 概念 | 是什么 | 用户视角 |
|------|--------|---------|
| **角色** | 给 agent 一个**名字 + 宽能力倾向**（不是固定职能岗位），它用这个脑子干活；名字承载累积协作史，倾向描述擅长的事 | "我要 Noel，他严谨、擅长结构化调研" |
| **任务** | 你要完成的事（看板上的卡片）；agent 每跑一轮是它的执行记录 | "去把这件事办了" |
| **房间** | 多角色 + 你坐一起讨论的地方（圆桌）；讨论完能直接拆成任务下发 | "大家来开个会" |

外加一个全局视角：

| **看板** | 所有任务的进度看板，你从这里盯全局、钻细节 | "现在都在忙什么，卡在哪" |

**这四个概念覆盖了你说的全部场景**：规划=房间产出 / 看板=追踪进度 / 头脑风暴=房间讨论 / 定时=agent 自主推进（后续）/ 任务下发=派活。

## 5. 你能做什么（用户故事）

### 第一期（先做这个）

```
1. 我建一个角色叫「Noel」，写清它好奇严谨、擅长结构化信息、默认用 search/read 调研并输出报告
2. 我建一个任务「调研 Multica 的看板实现」，派给 Noel
3. Noel 自动起一个带这个人设的 Claude，开干
4. 我在看板上看到这个任务从 待办 → 进行中
5. Noel 干完，任务变 待审核，我看结果、审批 → 完成
6. 同时派多个任务给不同角色（各自带不同能力倾向），看板上一目了然谁在忙
```

### 第二期（圆桌）

```
1. 我开个房间「下季度产品方向」，叫上 Noel（CTO 倾向）+ Mae（产品倾向）
2. 我抛出议题，两人轮流发言，关键决定自动记到白板（共享对话/任务状态，多 agent 共见；不是共享记忆池）
3. 讨论到一半我随时插话、纠偏
4. 讨论完一键把决定拆成任务，派给执行 agent
```

**协议级硬约束**（多 agent 同台必选——三轮走查 Buzz+Raft 独立收敛 + Paperclip 1266 个并发竞态 issue 反证：没有这些硬约束，多 agent 同台 99% 失败）：

- **沉默即成功**：agent 没事可报时默认不发，不强制每条消息都有回复（防 runaway ping 循环）。
- **串行轮次队列**：同一时刻只有一个 agent 发言，按队列轮转（防同秒抢答、防噪音爆炸）。
- **claim 硬约束**：任务被认领后他人不可重复认领（防重复劳动 / 并发竞态）。
- **Drop vs Queue 明确**：agent 拒绝/无法接任务时显式声明 Drop（丢弃回派活人）还是 Queue（排队等会），语义不模糊。

### 后续

- **定时任务**：agent 自己到点推进（如每天早上检查依赖、跑一轮 review）
- **团队**：一组 agent 配合干活（leader 带成员）
- **长记忆**：跨任务/跨房间记住上下文，不用每次从头解释

## 6. 第一期范围（明确做什么、不做什么）

**做**：
- 角色定义（创建/编辑角色，绑定人设 prompt + provider）
- 任务下发（建任务、派给角色、自动起 agent 执行）
- 看板（桌面拖拽看板 + 移动端列表）
- 审批闭环（agent 完成后你审批才算 done）

**不做（留后续）**：
- 圆桌房间（第二期）
- 定时任务（后续）
- 团队（后续）
- 向量检索长记忆（按需）

**第一期验收**：你能建角色 → 派任务 → agent 自动带人设执行 → 看板追踪 → 你审批闭环。整条链路通。

## 7. 需要你拍板的产品决策

调研已全部完成（见证据底座），方向有充分印证（Anthropic 官方的 Claude Tag + 多个开源项目 + 多轮社区走查独立收敛到同一套设计）。以下是我推荐的决策，你点头就定：

1. **第一期只做「角色 + 任务 + 看板」**，圆桌/定时/团队往后放。——认可？
   - 理由：Anthropic Claude Tag 自己都没做多 agent 角色，先把单 agent 多角色用法做扎实。
2. **agent 不能自己把任务标完成**，必须你审批。——认可？
   - 理由：你是老板，最终拍板权在你；agent 只能说「我做完了，请过目」。
3. **移动端不做拖拽看板，用按状态分组的列表**（进行中/待办/已完成折叠）。——认可？
   - 理由：手机窄屏拖拽看板体验差，列表更实用（Multica 实测结论）。
4. **任务记录先存本地文件**（对齐现有 session 存储方式），以后再升级数据库/上云。——认可？
   - 理由：先把产品跑通，存储形态后置；接口留好以后能平滑迁移。
5. **Codex 角色人设注入先降级处理**（Claude 干净支持，Codex 有已知 bug 待测，最坏情况第一期 Claude 角色全功能、Codex 角色简化）。——认可？
   - 理由：不阻塞第一期主线，Codex 细节后续补。
6. **每 agent 独立 identity + scoped 权限，绝不共享用户登录态**。——认可？
   - 理由：Grok Bot 让 bot 用用户账号登录 = accountability sink（责任黑洞），所有越权操作算到用户头上；OpenClaw CVE-2026-33579 CVSS 9.9 权限提升印证共享身份脆弱。私有部署是「数据不出本机」，独立 identity 是「责任不转嫁用户」——两层差异化。
7. **agent 按需唤醒 + 持久 context compaction，非全员 always-on**。——认可？
   - 理由：Grok Bot 内测者报告月 token 超过去 5 年总和、3 小时烧 52% 周额度；全员 7×24 在线不可持续。结合持久 context compaction（呼应三层模型「项目层焊 workspace」），按需唤醒省成本。
8. **「被允许沉默吗？」作为 agent 交互面设计的强制 checklist**（与 §5 圆桌「沉默即成功」同源）。——认可？
   - 理由：Buzz post-mortem（会话协议规则塞角色 prompt 触发 runaway reply loop）+ Raft held draft（Stay silent 是四选一一等选项）两产品独立收敛——多 agent 协作里「不发」和「发」同等重要，编排层不能默认每个 event 都触发 agent turn。

## 8. 不做什么（边界）

- **不重写现有 agent 运行时**——编排层是在现有 session runtime 之上加一层，runtime 零改动。
- **不做复杂的 agent 间协议**（Nostr / ACP 那套）——用简单的任务传递 + 共享状态（白板/任务/对话），够用。
- **不做共享记忆池**——协作靠共享状态（白板/任务/对话）+ 消息桥，agent 间不互读记忆。每个 agent 有自己的私有记忆，靠在共享状态里「说话」交换 finding（Raft 反对共享 brain pool 会「deletes the specialists」——溶解掉专家分工）。
- **不强求上云**——先本地服务器跑稳，Cloudflare 接口留好，以后能迁再迁（agent 需要 PTY/终端，全上云有硬障碍，混合部署是务实终态）。
- **不伪造数据**——所有 agent 能力、任务进度、历史都是真实运行态，UI 不假装完整。

## 9. 演进路线（一张图）

```
第一期（现在）          第二期                 后续
─────────────         ─────────────         ─────────────
角色 + 任务 + 看板  →   圆桌房间          →   定时任务
  ↓                    ↓                    团队（leader+成员）
跑通单 agent          多角色讨论 +          长记忆（向量检索）
多角色用法            拆任务下发            Cloudflare 迁移
```

每一步都遵循：先在本地跑通验证，再扩展；每个功能都先用真实数据验证再打磨 UI。
